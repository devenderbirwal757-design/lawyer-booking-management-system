### 3.1 Service-driven slot generation (D4)

**Spacing rule (settled):** step = `service.duration_minutes + service.buffer_after_minutes`,
walked forward from the working-hours start. There is no other spacing field.

- `buffer_after_minutes` defaults to **5** (D4), `buffer_before_minutes` defaults to **0**.
  Both are per-service and overridable. Five minutes is turnaround — writing notes,
  escorting the client out, a bathroom break. Zero before, because a client arriving early
  is not a problem worth modelling.
- Buffers are **not** shown to the client. The slot label is the start time; the client does
  not need to know the lawyer needs 5 minutes afterwards, and surfacing it invites
  "can I book 10:35 then?" questions the answer to which is no.
- A buffer may push the last slot past closing time. That is correct: the consultation ends
  at 13:00 and the lawyer takes 5 minutes to close it out. Do not truncate the final slot to
  keep the buffer inside the working window.

```
provider works 10:00-13:00, buffer_after = 5, consultation must fit before 13:00

30-min service  ->  10:00  10:35  11:10  11:45  12:20 (ends 12:50)
45-min service  ->  10:00  10:50  11:40 (ends 12:25)
```

(`12:55` and `12:30` start-times appeared in an earlier draft of this section as
the day's last slots. They are wrong: the consultation itself - `start +
duration` - must end before closing, so a 12:55 or 12:30 start can never be
offered. What *may* overrun is the buffer: see below.)

**The one visible consequence of D4 worth a sanity check:** slots land on `:35`, `:50`,
`:20` rather than round times. That is the honest output of `duration + 5`. The
alternative — snapping to the nearest 15 or 30 — reintroduces exactly the fixed grid D4
removes, and reintroduces the fragmentation it was meant to fix. If `:35` bothers you, the
clean way to get round times is `buffer_after_minutes = 0` on that service, which yields
`10:00 10:30 11:00 …` and reproduces the PRD §6 example exactly. Both are valid; the buffer
costs you nothing in bookings and buys five minutes of sanity.

**Why anchoring matters, and the failure it prevents.** With two services of different
durations you get two interleaved grids. Without anchoring, a 45-minute booking at
10:00-10:45 leaves a 10:45-11:00 gap that *no* service can use — 30 minutes does not fit,
and 45 minutes cannot start there. Anchored, the 30-minute client is offered 10:35 instead,
and the unusable gap never appears. Without this rule availability fragments wherever two
durations interleave, and the calendar looks half-empty for no reason.

`SlotService.slots(provider, service, date)` therefore computes: working hours for that
weekday, plus any day-level `OVERRIDE` exception, minus `BLOCKED` exceptions, minus every
appointment in an active status (D5), then walked forward in `duration + buffer_after`
steps from the working-hours start, keeping only starts whose full span fits before closing.

**One thing service-driven does not change:** the display. The slot grid renders whatever
the API returns, so the frontend must not assume 30-minute rows. See F §4 step 2.

## 5. Double-booking prevention (the critical part)

> Implements [`prd.md`](./prd.md) §7 and §31's final acceptance line. This is the only S0
> severity area in the project — see S §A8 and the release gate
> in §1. Frontend counterpart: [`frontend-plan.md`](./frontend-plan.md) §4 (slot refetch + 409 recovery).

Four layers, all server-side:

1. **Slot generation is server truth.** `SlotService.get_slots(provider, service, date)` = recurring rules ∪ day exceptions − blocked times − active appointments − expired holds − lead-time and look-ahead limits. Step size = `max(slot_interval, service.duration + buffers)`.

2. **PostgreSQL exclusion constraint — the real guarantee.** Because durations differ per service, a plain unique `(provider, start_at)` is not enough (10:00 60-min vs 10:30 30-min overlap).
   ```sql
   CREATE EXTENSION btree_gist;
   ALTER TABLE appointments ADD CONSTRAINT no_provider_overlap
     EXCLUDE USING gist (
       provider_id WITH =,
       tstzrange(start_at, end_at, '[)') WITH &&
     ) WHERE (status IN ('PENDING_PAYMENT','CONFIRMED'));
   ```
   Any race condition is resolved by the database, not by application logic.

3. **Slot hold + expiry.** `POST /appointments` inserts the row in `PENDING_PAYMENT` with `slot_hold_expires_at = now + 10 min`. A Celery task sweeps expired holds → `CANCELLED` (or a dedicated `EXPIRED` status). Prevents abandoned carts from blocking real bookings.

4. **Serialization + retry.** Wrap creation in `transaction.atomic()` and retry on `IntegrityError` up to N times, returning `409 SLOT_UNAVAILABLE`. Optionally take a `pg_advisory_xact_lock` on `hash(provider, date)` as a cheap pre-check. If the exclusion constraint is too heavy at scale, fall back to `SELECT ... FOR UPDATE` on the provider row.

Idempotency: `POST /appointments` accepts an `Idempotency-Key` header so a double-tap on mobile can't create two holds.

**Required test:** two threads, same provider + slot, `transaction.atomic()` each → exactly one 201, one 409.

### 5.5 Automatic blocking (D5)

Booking a time blocks it with no admin action. There is nothing to toggle and no
"mark as busy" step — the block *is* the appointment row, and the availability query
subtracts it. This removes a whole class of bug: a slot that looks free in the UI because
somebody forgot to block it.

- A `PENDING_PAYMENT` appointment blocks the slot for the duration of its hold, not just
  for confirmed bookings. Otherwise two people could hold the same 11:30 and only one would
  ever pay. Layer 3 handles this; layer 2's exclusion constraint covers it under races.
- `COMPLETED`, `CANCELLED`, `NO_SHOW` and `RESCHEDULED` do **not** block. The query filters
  on the active statuses only, matching the constraint's `WHERE` clause. These two must be
  kept in sync — see the invariant test below.
- **Manual blocking is now for exceptions only**: lunch, a court appearance, a personal
  afternoon. `AvailabilityException` type `BLOCKED`.
- **New validation this forces:** a `BLOCKED` exception may not overlap an existing
  appointment. Reject it with `409 SLOT_OCCUPIED` and tell the lawyer to cancel or
  reschedule the appointment first. Without this, blocking over a booked slot produces a
  state where a confirmed appointment sits inside a blocked window, and the lawyer has to
  reason about which one wins. The appointment wins, and the admin is told.
- Same validation in reverse: rescheduling an appointment into a blocked window is rejected
  by the same overlap check as any other booking — an exception is not a back door around
  layer 2.
- Admin UI copy (F §6) must distinguish the two: "Block time" = a gap in the schedule with
  nothing booked, versus cancelling a booking. Same intent, different consequences, so
  they get different buttons.

**Invariant test (add to CI):** for every provider, assert no two appointments in an active
status overlap, and assert no active appointment overlaps a `BLOCKED` exception. Run it as
a periodic task as well as a test, so a migration or manual DB edit cannot quietly break
the invariant without anyone noticing.

## 6. Payments

**Decisions applied:** D1 Razorpay · D2 refunds are manual (see §11).

- `PaymentGateway` ABC: `create_order()`, `verify_signature()`, `fetch_order()`, `create_refund()`.
- `RazorpayGateway` is the live implementation. `CashfreeGateway` raises
  `NotImplementedError` — a stub whose only job is to prove the seam is real.
- `POST /payments/create-order` — server recomputes the amount from the `Service` price. Amount from the client is ignored.
- `POST /payments/webhook`
  1. Read raw body, verify `X-Razorpay-Signature` with the shared secret (constant-time compare).
  2. Persist raw payload to `PaymentEvent` **before** processing; dedupe on `event_id`.
  3. `select_for_update` the `PaymentOrder`; apply state transition only if legal.
  4. On `payment.captured`: `Payment → SUCCESS`, `PaymentOrder → SUCCESS`, `Appointment PENDING_PAYMENT → CONFIRMED` (same transaction), enqueue confirmation email.
  5. Unmatched/duplicate/invalid events are logged and return 200 (gateways retry on non-2xx).
- **Fallback:** `GET /payments/{id}/status` polls the gateway and reconciles — covers a missed webhook.
- **Reconciliation task:** hourly Celery beat job compares `PENDING`/`CREATED` orders older than 30 min against the gateway and marks `FAILED`.
- Never mark a payment successful from a client call. There is no such endpoint.

### 6.1 Payment state machine

Payment is a state machine, never a boolean. Legal transitions are declared once in
`payments/state.py` and asserted by tests; any other transition raises.

```
CREATED ──> PENDING ──┬──> SUCCESS ──> REFUNDED
                      ├──> FAILED
                      ├──> EXPIRED
                      └──> CANCELLED
```

`SUCCESS` is terminal except for `REFUNDED`. `FAILED`, `EXPIRED` and `CANCELLED` are terminal.

- `PENDING → EXPIRED` fires when the appointment's slot hold expires before payment lands
  (B §5 layer 3, `slot_hold_expires_at`). The `expire_slot_holds` beat task cascades this.
- `PENDING → CANCELLED` when the client abandons and releases the hold.
- The appointment is confirmed **only** in the same transaction that moves
  `Payment → SUCCESS`. There is no other path to `Appointment.CONFIRMED`.

> **Deviation from the PRD, flagged for sign-off.** PRD §12 lists five statuses
> (`CREATED`, `PENDING`, `SUCCESS`, `FAILED`, `REFUNDED`). `EXPIRED` and `CANCELLED` are
> additions, not replacements. They exist because the slot hold in B §5 can expire or be
> released while a payment is still in flight, and without those two states an abandoned
> checkout would be indistinguishable from a failed one — which makes the reconciliation
> task in S §A5 unable to tell "we gave up" from "the gateway declined". Confirm this is
> acceptable, or fold them back into `FAILED` and lose that distinction.

### 6.2 Manual refunds (D2)

No automatic refund path exists. The flow is deliberately human-in-the-loop:

```
Admin cancels appointment (client or lawyer-initiated)
   │
   ├─> if paid: create Refund row, status PENDING_ACTION
   │             lawyer initiates the refund in the Razorpay dashboard
   │             admin marks it settled:  Refund -> SETTLED
   │             Payment -> REFUNDED        (two separate admin actions)
   │
   └─> if unpaid: nothing to refund, appointment CANCELLED only
```

- `POST /admin/payments/{id}/refund` creates a `Refund` in `PENDING_ACTION` and writes an
  audit entry. It does **not** call the gateway and does **not** flip `Payment` to `REFUNDED`.
- `POST /admin/refunds/{id}/settle` is the only thing that moves `Payment → REFUNDED`.
- `PaymentGateway.create_refund()` is intentionally left unused in MVP. It stays on the ABC
  so an automatic refund path can be added in Phase 2 of the product without touching the
  interface. Security.md §A5 covers both transitions.
- Consequence for the client-facing copy: the UI must never promise an automatic refund.
  It states the cancellation outcome honestly (F §5, cancel dialog) and the refund is
  communicated separately once the lawyer settles it.

### 6.3 Phone-OTP-only identity (D3)

No required email. Consequences, all of which are deliberate:

- `Customer.email` is nullable and unique-per-tenant when present. `Customer.phone` is the
  identity key, normalised to E.164 and unique per tenant.
- The booking wizard still **offers** an email field (F §4 step 3) but does not require it.
  Clients who skip it simply have no email on file.
- Client auth is OTP-only. There is no client password, no password-reset flow, and nothing
  to breach via leaked credentials — the account is only reachable by someone holding the
  phone. This is a genuine security win, and it is why S §A3 concentrates on OTP abuse and
  enumeration rather than on passwords.
- **Email notifications become best-effort, not guaranteed.** This is the one real cost and
  it contradicts two PRD must-haves, so it is called out rather than buried:

  | PRD requirement | Status under D3 |
  | --- | --- |
  | §30 "Email confirmation" | Delivered only to clients who supplied an email. A booking by an OTP-only client gets no confirmation email. |
  | §19 reminders 24h / 1h | Same. No email means no reminder channel for that client. |

  Three ways out, pick one before Phase 7:
  1. **Prompt for email at step 4**, framed as "so we can remind you" — keeps the PRD
     must-haves for most clients without making it a hard gate. Cheapest.
  2. **Require email only at payment time.** Strictly satisfies §30/§19; reintroduces friction.
  3. **Accept the gap for MVP** and record it as a known deviation in prd.md §33. Reminders
     then reach only opted-in clients, and the "no-show reduction" goal is not actually met.

  Recommendation: option 1. Option 3 is defensible only if WhatsApp (already deferred in
  PRD §30) is on the roadmap as the reminder channel.

- `send_notification` must not treat a null `to_address` as an error. It records the
  notification as `SKIPPED_NO_CHANNEL` so the audit trail shows the attempt, rather than
  retrying forever or silently dropping it.

## 7. Notifications & reminders

- `NotificationService` dispatches by channel to a `Channel` interface (`EmailChannel` MVP; `SmsChannel`/`WhatsAppChannel` stubs).
- Templates in `notification_templates` with `{{ placeholders }}`; seeded on migrate via data migration. `BOOKING_CONFIRMED`, `PAYMENT_SUCCESS`, `BOOKING_CANCELLED`, `BOOKING_RESCHEDULED`, `REMINDER_24H`, `REMINDER_1H`.
- Queue: `send_notification(notification_id)` task, retries 3× with backoff, records `attempts`/`last_error`. A dead-letter sweep marks permanent failures.
- Reminders: when an appointment is confirmed, insert two `Reminder` rows (offsets from tenant settings, default 24h/1h). Beat task `dispatch_due_reminders` runs every 5 min, claims rows with `select_for_update(skip_locked=True)`, so it is safe across multiple workers and never double-sends (`UNIQUE(appointment, kind)`).
- All sends happen outside the request/response cycle (transaction.on_commit).

## 8. Auth, authorization, security

- Admin: `django.contrib.auth` with email login + SimpleJWT. `IsAdmin` permission class.
- Client: phone OTP — hashed, 5-min TTL, 6 digits, max 5 attempts/number/hour, 10/hour/number send limit. Verification upserts the `Customer` row. Tokens are short-lived access + refresh.
- **Ownership enforcement:** every customer endpoint resolves the target via `Appointment.objects.filter(customer=request.customer)`; admin endpoints check `request.tenant`. There is a shared `common/permissions.py` — no ad-hoc `if` in views.
- Rate limiting: DRF throttle scopes for OTP, booking-create, webhook, and login.
- Input validation: all writes through DRF serializers; prices/durations as `Decimal`/`PositiveInteger` with upper bounds.
- CORS allowlist, HTTPS/HSTS, secure cookies, `SECURE_PROXY_SSL_HEADER`, DRF `SECURE_SSL_REDIRECT` in prod.
- `X-Request-ID` middleware + structured logging with request ID.
- Raw webhook body must bypass DRF's multipart parsing.
- DB: least-privilege app user, automated daily `pg_dump` to S3 with retention, restore drill documented.

> Implementation notes (Phase 5): a booking is *not* a row insert, it is a
> revalidation — the client's slot id is re-derived from the provider's rules,
> exceptions, live appointments and lapsed holds, and the server's own duration
> wins (the client cannot ask for a cheaper, longer appointment). Holds are
> `PENDING_PAYMENT` and expire after `SLOT_HOLD_MINUTES`; the beat sweep
> (`appointments.expire_slot_holds`, every ≤15 min) is what actually releases
> them, with `skip_locked` so two workers cannot double-sweep.
>
> Double booking is prevented twice, deliberately: the service checks and
> answers `409 slot_unavailable`, and a `RunSQL` migration adds a `btree_gist`
> exclusion constraint on
> `(provider_id WITH =, tstzrange(start_at, end_at, '[)') WITH &&) WHERE status
> IN (PENDING_PAYMENT, CONFIRMED)` as the race-proof backstop. The buffer is
> excluded from `end_at` (turnaround, not billable time) but *is* included in
> the busy span availability subtracts. A losing insert surfaces either as
> `IntegrityError` **or** as a PostgreSQL deadlock/serialisation abort while
> the two index probes are ordered - both are translated into the same 409, so
> a genuine race is never a 500. `PENDING → EXPIRED` is the *only* path to
> `EXPIRED` (S §A8), and a `BLOCKED` exception may not be created over an
> active appointment (`409 slot_occupied`).
>
> `Idempotency-Key` is optional but must be a UUID when present; a replay
> resolves the original hold and answers `200` with the same body, so a
> double-tap cannot carve a second appointment. Auth is split by scope:
> `BookingViewSet` / `CustomerAppointmentViewSet` authenticate with
> `CustomerJWTAuthentication` and scope every read through
> `customer=request.customer`, so another customer's appointment is a 404 and
> never a 403 (S §A4). Admin transitions are actions, not a field write - a
> `PATCH status=…` is refused with `400` and notes are the only editable
> field - and a paid service cannot be confirmed by hand until its payment
> lands (open Q6, §6.1).

### Guards added while hardening this (not in any phase above)

These are project-enforced invariants that no checklist box records, so they are
recorded here:

- **Tenant resolution is checked at boot.** `manage.py check` warns
  (`tenants.W001`) when `DJANGO_DEFAULT_TENANT_SLUG` is unset and **errors**
  (`tenants.E001`/`E002`, non-zero exit) when it is set but does not resolve to an
  active practice. Unset is a warning because subdomain and `X-Tenant-Slug`
  routing legitimately need no default. The unset failure is silent — a
  tenant-scoped list answers `200` with `count: 0` — which is why it is a check
  and not a test. `TenantContextMissing` also returns a named `500` envelope
  instead of a generic one.
- **No tenant-scoped viewset may override `get_queryset()` without `super()`**
  (`tests/unit/test_tenant_queryset_guard.py`). This drops the tenant filter and
  reads the whole table. One declared exemption exists
  (`AdminPaymentEventViewSet`, whose model has no `tenant` column) and must carry a
  justification in its own class body.
- **`filterset_fields`/`filterset_class` are banned on tenant-scoped viewsets**
  (`tests/unit/test_filterset_guard.py`). A relation field publishes every
  practice's identity through the related model's `_default_manager`, and
  constructing a filterset needs a bound tenant, so it breaks list requests and
  schema generation. `_filter_params()` in `apps/payments/views.py` is the
  sanctioned alternative.
